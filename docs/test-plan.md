# Test Plan — Stellar Burgers UI Autotests

> Документ описывает подход к тестированию **до начала работ**. Фактические результаты прогона — в [test-summary.md](test-summary.md).

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Объект тестирования | Веб-приложение Stellar Burgers (учебный стенд) |
| Вид тестирования | Функциональное UI-тестирование |
| Вид автоматизации | Регрессионный прогон ключевых пользовательских сценариев |
| Стенд | Публичный учебный стенд Stellar Burgers |

## 2. Цель

Автоматизировать ключевые пользовательские сценарии — регистрацию, вход в аккаунт через все доступные точки входа и навигацию по разделам конструктора — чтобы изменения UI не ломали базовые функции незаметно.

## 3. Объём тестирования

### В объёме

- **Регистрация**: создание пользователя с валидными данными; негативная проверка с паролем короче 6 символов.
- **Вход в аккаунт**: все четыре точки входа — кнопка «Войти в аккаунт», личный кабинет, форма регистрации, форма восстановления пароля.
- **Конструктор**: переход к разделам «Булки», «Соусы», «Начинки» по клику на вкладку, включая проверку прокрутки контейнера.

### Вне объёма

- **API-контрактные проверки** — REST-клиент используется только как вспомогательный слой: подготовка и очистка тестовых данных в фикстурах (`@Before` / `@After`). Проверки — на уровне UI.
- Оформление заказа, история заказов, личный кабинет после входа.
- Кроссбраузерная матрица: полный прогон — на одном браузере; поддержка Chrome, Firefox и Yandex Browser реализована на уровне фабрики драйверов.

## 4. Подход

- Позитивные и негативные проверки по ключевым сценариям.
- **Page Object Model** — каждый экран как отдельный класс, базовые элементы в `BasePage`.
- **WebDriver Factory** — единая точка создания драйвера, выбор браузера параметром.
- **Параметризация** — один тест-метод покрывает несколько наборов данных (точки входа, разделы конструктора).
- **Тестовые данные** — генерация уникальных пользователей (Faker); создание и удаление — через вспомогательный REST-клиент в фикстурах, чтобы прогоны не зависели от остаточных данных на стенде.
- **Отчётность** — Allure.

## 5. Критерии входа

- Стенд доступен, не в окне технических работ.
- Окружение настроено: JDK 11, Maven, драйверы браузеров.
- Тестовые пользователи создаются с уникальными email (без конфликтов с прошлыми прогонами).

## 6. Критерии выхода

- Все кейсы чек-листа (раздел 8) выполнены, по каждому записан вердикт «пройден» или «не пройден».
- По каждому не пройденному кейсу установлена причина; ошибки продукта описаны в баг-репортах с шагами воспроизведения.
- Выполнен повторный прогон набора, чтобы убедиться, что результаты воспроизводятся, а падения не случайны.
- Результаты сведены в отчёт о тестировании со статистикой и рекомендациями для следующей итерации.

## 7. Окружение и инструменты

| Компонент | Версия / решение |
|---|---|
| Java | JDK 11 |
| Сборка | Maven |
| UI-автоматизация | Selenium WebDriver |
| Управление драйверами | WebDriverManager (Chrome, Firefox); Yandex Browser — локальный драйвер |
| Тестовый фреймворк | JUnit 4 |
| Отчёты | Allure |
| Вспомогательный REST-клиент | Rest Assured + Gson |
| Генерация данных | Faker |

**Браузеры:** Chrome и Firefox — через WebDriverManager; Yandex Browser — через локальный драйвер (см. риски).

## 9. Риски и ограничения

- **Selenium 3 (EOL с октября 2023)** — возможны несовместимости с новыми версиями драйверов; в планах переход на Selenium 4.
- **Yandex Browser через локальный драйвер** (`C:/WebDriver/bin/yandexdriver.exe`) — запуск на другой машине требует ручной настройки пути; в планах вынос пути в конфигурацию.
- **Нестабильность из-за сети** — сетевые задержки могут давать flaky-результаты; заложены разумные явные ожидания.

## 10. Отчётность

- Allure-отчёт по каждому прогону.
- Сводка фактических результатов — в [test-summary.md](test-summary.md).
